# 主角成长体系 v2：修正后的 C 方案（2026-10-02 定案）

> 取代 `设计_主角成长_三方案.md` 的结论位置（三方案文件保留为过程记录）。
> 用户裁决：**选 C，比例上限 +10%**；并对 C 做两处修改：**任务只管技能、属性改由随机事件积攒**；
> 新增**弹性补偿机制**（属性落后于技能时多刷属性事件）。

---

## 一、主角成长的最终形态

```
【挂机线】做任务 ──→ 技能经验（细密）──→ 产出量 / 稀有度
                                        ↓
                              解锁高品质任务（产物 = 高品质物品）

【在线线】处理随机事件 ──→ 属性经验（细密）──→ 四维属性

【跨线】个人等级 ──→ 自由点 ──→ 属性【修正 ±10%】

【阶梯】称号（技能/属性达标解锁，可随时切换，决定主角作战方式）
【阶梯】品级 → 官职（功勋驱动，必须在线）
```

| 系统 | 来源 | 粒度 | 玩家操作 | 承担的职责 |
|---|---|---|---|---|
| **技能**（7–10 个） | **只由挂机任务** | 细密 | 排任务顺序（少跑路） | **挂机的深度** |
| **属性**（四维） | **只由随机事件** | 细密 | 上线处理事件 | **在线的深度** |
| **自由点** | 个人等级 | 离散 | 分配（±10% 修正） | 补短板 / 强化倾向 |
| **称号** | 技能 / 属性达标 | 阶梯 | 随时切换 | **主角作战方式** + 品质偏向 |
| **品级 / 官职** | 功勋 | 阶梯 | 在线 3 选 1 | 额外倍率 + 事件属性偏向 |

> 🔑 **两条线彻底分离：挂机管技能，在线管属性。**
> 这解决了 V1 遗留的"技能与属性职责耦合"问题，且让**挂机和在线各有一条独立成长线**，
> 两条线**不互相抢**，也**不互相阻塞**。

## 二、挂机线：技能（7–10 个）

| 项 | 定案 |
|---|---|
| 数量 | **7–10 个**，与挂机任务类型**一一对应** |
| 成长 | **只由做对应任务**，细密（连续经验条） |
| 作用 | ① 该类任务**产出量倍率**；② **解锁高品质任务 / 高品质产物** |
| **不动时长** | ✅ **技能不缩短作业与移动时长**（保住 V1 的 131 任务/天节奏基线） |

### 🔴 关键约束：挂机层的信息量必须收敛

**挂机层已经承载了 2 个维度的信息**：

| # | 维度 | 内容 |
|---|---|---|
| 1 | **拖任务顺序** | 少跑路（主要的操作乐趣） |
| 2 | **高品质任务提示** | 惊喜点（高品质物品奖励） |

> ✅ **因此任务种类不宜多** —— 种类一多，玩家在"拖顺序"时要同时权衡的东西就超出可读范围，
> 操作从"顺手的排序"退化成"需要算的规划"。
>
> **建议取 7 个**（沿用 V1 的 6 类 + 讨伐），而不是上限 10。
> 若后续内容量确实需要，再通过**高品质任务的差异化**（而不是加新任务种类）来扩。

| 项 | 定案 |
|---|---|

| 内容丰富度 | ✅ **需要内容丰富，种类可能远多于挂机任务** |

> 是有意的分工：**挂机求可读，事件求丰富。**

## 四、🔑 弹性补偿机制（本次新增，我认为这是整套设计的亮点）

| # | 弹性 | 触发 | 作用 |
|---|---|---|---|
| **①** | **事件属性偏向** | 受**称号 / 官职**影响 | 刷出的事件有属性倾向 → 配合玩家当前路线（与 V2-19 称号联动） |
| **②** | **属性补偿** | 玩家**总属性 < 总技能等级所预期匹配的水平** | **多刷属性事件** |

### ② 是什么意思（Q5 已定：**随等级判断**）

> ✅ **Q5 定案：预期匹配水平的基准 = 玩家【个人等级】**（不由离线时长直接推算）。
>
> | 判定量 | 说明 |
> |---|---|
> | **预期总属性** = `f(个人等级)` | 读配置表，等级 → 预期总属性 |
> | **当前总属性** | 四维之和 |
> | **gap = 预期 − 当前** | gap > 0 即"落后" |
>
> **为什么用个人等级做基准**：个人等级是"**总量**"层（V2-1），单一标量、单调递增、
> 天然与挂机时长正相关。用它比直接算离线时长更稳定（不受掉线 / 多设备 / 时间戳问题干扰）。
>
> | 情形 | 含义 | 系统反应 |
> |---|---|---|
> | gap ≤ 0 | 属性不落后 | 正常刷 |
> | **gap > 0** | **离线挂机太久 / 在线时间不足** | **多刷属性事件 → 快速追平** |

### ③ 具体算法（Q6 已定）

```
每日结算：
  gap        = 预期总属性(个人等级) − 当前总属性        ← 直接算差多少属性
  needTotal  = gap × 90%                                ← 5 日窗口目标追平量（读配置）
  needPerDay = needTotal / 5                            ← 每日目标属性量
  evtNeed    = needPerDay / 单个属性事件平均产出         ← 换算成"每天插几个属性事件"
  evtCap     = 当日事件总数 × 10%                        ← 硬上限（读配置）

  每日插入的补偿事件数 = min( evtNeed , evtCap )
```

| 分支 | 结果 |
|---|---|
| `evtNeed ≤ evtCap` | ✅ 约 **5 日**追到 **90% 的差距** |
| `evtNeed > evtCap` | ⚠ 按 **10% 上限**刷 → **追平时间 > 5 日**（差得越多，天数越多） |

> ✅ **本机制不补偿到完全追平**（用户明确）。

**三个设计上的好处**

| # | 好处 |
|---|---|
| 1 | **它是相对量而非绝对量** —— 上限挂在"当日事件总数"上，天然随游戏进度缩放，不需要重新调参 |
| 2 | **它自动做难度分档** —— 差得少 5 天追上；差得多就慢慢追，**不会出现"一口气补满"** |
| 3 | **它与约束③同源** —— 10% 这个上限本身就是在保证"补偿路径永远弱于正常在线" |

**⚠ 一个需要注意的数学性质（可选优化）**

> `needTotal = gap × 90%` 每天重算 → gap 会**指数衰减**（半衰期约 1.5 天）→ **渐近趋近于 0**。
> 因此"不完全追平"在数学上成立（永远差一点点），但**实际会收敛到极小值**。
>
> → 若你希望**永久保留一个可感知的差距**（让在线始终有意义），需要额外加一条**地板**：
> `gap < X（如 5% 的预估值）→ 停止补偿`。**要不要加，请定。**

### 4 个配置项（Q6 落地所需）

| 参数 | 建议默认 | 说明 |
|---|---|---|
| **预期总属性曲线** | 读表 | `预期总属性 = f(个人等级)` |
| **追平窗口** | 5 日 | 目标天数 |
| **追平比例** | 90% | 单窗口追平比例 |
| **每日补偿事件占比上限** | 10% | 相对**当日事件总数** |
| **单个属性事件平均产出** | 读表 | 用于「属性量 → 事件条数」换算 |


**为什么这条设计好（三个理由）**

| # | 理由 |
|---|---|
| 1 | **它把"在线"的价值从"必须"改成了"可以补"** —— 玩家即使挂机很久，也不会永久掉队 |
| 2 | **它与 V2-36 的惩罚形成了正向配对**：V2-36 罚的是"错过事件"（失去内容），这条补的是"属性落后"（追上进度）。**一罚一补，玩家感觉是"被追赶"而不是"被抛弃"** |
| 3 | **它天然服务于上线预算**：补偿事件是高频、低决策成本的（就是拿属性经验），可以在列表里批量处理，不撑爆 20 分钟预算 |

### 🔴 但必须补一条上限，否则会变成"故意不处理事件"的最优解

> 若补偿无上限 → 玩家会发现"**不处理事件 → 属性落后 → 系统猛补属性事件**"，
> 于是**故意不登录**反而收益更高。这会**直接摧毁"拉登录"的设计目标**。

| # | 必要约束 | 建议 |
|---|---|---|
| ① | **补偿有上限** | 补偿只追平到"预期水平"为止，**不能超过**（预期 = 按挂机时长的基准值） |
| ② | **补偿只给属性，不给品质** | 补偿事件**不给高品质产物 / 名品**（避免变成刷宝捷径） |
| ③ | **补偿率的斜率要低于正常在线** | 正常在线处理事件的总收益，必须**严格高于**补偿路径（否则在线无意义） |

> ✅ 一句话：**补偿让玩家"追得上"，但永远"追不赢"。**

## 五、验证：这套结构解决了什么

| 原问题 | 现在 |
|---|---|
| 技能与属性职责耦合 | ✅ 分离：技能=挂机，属性=在线 |
| 一次任务发两份经验 | ✅ 只剩技能经验 |
| 技能零玩家表达 | ✅ 表达在"排任务顺序"（挂机层的主操作） |
| 自由点无处可去 | ✅ 属性 ±10% 修正 |
| 挂机层信息过载 | ✅ 任务种类收敛到 7 |
| 事件层内容单薄 | ✅ 事件种类可远多于任务 |
| 离线惩罚后无法挽回 | ✅ **弹性补偿兜底** |
| 补偿可能反噬成"故意不登录" | ✅ 三条约束（有上限 / 只给属性 / 斜率低于正常） |

### 7.3 🔑 技能如何间接影响属性（建议，待确认）

**问题**：属性改由事件产出后，出现一个叙事缺口——
**做"训练"任务不涨武力了**，那玩家的战斗能力从哪来？全靠上线处理事件。

**建议的桥**：让**技能的属性倾向**去影响**事件的属性偏向**（接 §四 弹性机制①）。

| 技能 | 倾向属性 |
|---|---|
| 武艺、矿冶、兵法 | **武力** |
| 交游、兵法 | **统帅** |
| 经学 | **智力** |
| 货殖、农桑 | **政治** |

> 效果：**训练技能练得越高 → 越容易刷出武力类事件 → 武力涨得越快。**
>
> | 好处 | 说明 |
> |---|---|
> | 不违反"任务只管技能" | 技能**不直接给属性**，只**改变事件偏向**（间接、软性） |
> | 玩家有了"引导属性方向"的工具 | 想练武力 → 多挂训练任务；这是挂机层与在线层之间**唯一的、也是最自然的**接口 |
> | 与弹性机制①同构 | 弹性①是**称号/官职**影响偏向，这里加**技能**作为第三个影响源，规则统一 |
>
> → 覆盖面检查：**武力 3 / 统帅 2 / 智力 1 / 政治 2**，四维全覆盖 ✅
> ⚠ 智力只有 1 个来源，可能偏窄 → 建议给智力再补一个（如 **经学 + 交游 → 智力**，或新增技能时补）

## 八、主角成长：最终结构图

```
【挂机线】排任务顺序 ──→ 做任务 ──→ 技能经验（7 个，细密）
              ↑                          │
   拖顺序少跑路 / 高品质惊喜            ├→ 该类任务产出倍率
              │                          └→ 解锁高品质任务与高品质产物
              │                                    │
   技能倾向 ───┴──────────────────────────────┐    │
                                              ↓    ↓
【在线线】处理随机事件 ──→ 属性经验 ──→ 四维属性    货品 ──→ 跑商
              ↑                    ↑
   事件偏向（称号/官职/技能）   自由点 ±10% 修正
              ↑
   弹性补偿：属性落后于 f(个人等级) → 多刷属性事件（5日追90%，≤当日事件总数10%）
```
