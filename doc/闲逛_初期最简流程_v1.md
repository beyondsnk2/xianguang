## 一、流程原文（用户口述，无删改）

1. 一块地图，暂定 **36 × 30 格**，每格 **30 像素**
2. 格子上有若干**点**，占地 **1 到 4 格**不等
3. 点的类型：州府、兵营、街市、农田、酒馆、书院、矿山
4. 点之间由**路线**连接
5. 一个州府附近的点**从属于**这个州府；**道路点不从属于州府**（mapNode）
6. 玩家初期出生在一个州府地块中
7. 系统随机生成一个玩家可见的**任务列表**，列表中任务完成一个以后，**3 分钟后补充一个**
8. 任务内容：「去 XX 城市做 XX」
9. 角色自动按顺序，沿路线去往当前执行的任务地点，完成后重复
10. 玩家可手动拖动任务改变顺序；**不允许拖动已经在执行的任务**（到达地点后才开始执行）
11. 完成任务获取**道具**，并获得**属性经验**
12. 完成任务后，若**背包满了**，需要回到城市放入仓库，再去执行下一个任务

## 三、任务生命周期状态机

```
待执行 ──(成为队首)──→ 移动中 ──(到达)──→ 执行中 ──(needTime)──→ 结算
  │                      │                │                       │
可拖动排序           拖动锁定          拖动锁定          发道具 + 属性经验
                                                                  │
                                            ┌─────────────────────┴─────────────────────┐
                                       背包未满                                     背包已满
                                            │                                           │
                                            └───────────→ 回州府存仓 ←──────────────────┘
                                                                  │
                                                      该任务出列，后续任务整体上移
                                                                  │
                                                      空槽移到队尾（独立计时 180 s）
                                                                  │
                            空槽计时到点 → 新任务补在任务区末尾（空槽之前）→ 回到「待执行」
```

> **队列不变量：任务区在前，空槽恒排队尾。** 任务完成即出列，不再原地留坑。

### 3.1 状态定义

| 状态 | 进入条件 | 玩家可拖动 | 逻辑内容 |
|---|---|---|---|
| 空槽 | 任务结算完成 | — | **位于队尾**，独立计时 180 秒，到点生成新任务并插到任务区末尾 |
| 待执行 | 生成成功 / 后续任务上移 | **是** | 静默等待成为队首 |
| 移动中 | 成为队列中的第一个任务 | 否 | 沿路线前往目标节点，消耗移动时间 |
| 执行中 | 到达目标节点 | 否 | 消耗 `needTime`，到点结算 |
| 结算 | `needTime` 归零 | — | 发放道具 + 属性经验，**该任务出列** |
| 回州府存仓 | 结算后背包 > 容量 | 否 | 移动到州府节点，全部入仓，清空背包 |

### 3.2 关键规则

- **列表即队列**：玩家可见列表 = 执行队列，永远按队首执行。玩家能改的只有「未来」，不影响当前，逻辑干净。
- **列表长度恒定**：完成一个即**出列**，后续任务整体上移，空槽落到**队尾**并在 180 秒后补回任务区末尾，
  列表不会出现「空转」。**不变量：任务区在前，空槽恒排队尾**（玩家拖动排序后同样归位）。
- **回城全自动**：结算后若超载，系统自动插入「回最近州府 → 全部入仓 → 清空背包」，再继续下一个任务。这是离线收益得以成立的前提。

## 六、建议：离线结算用离散事件推进

不要逐秒 tick，按「下一个事件的时间点」跳跃推进，在线离线共用同一套逻辑：

```
state = { now, pos/路段进度, 当前阶段剩余, queue[], 每槽补位倒计时, 背包, 属性, 经验 }

tick(state, elapsed):
  while elapsed > 0 and elapsed_used < OFFLINE_CAP:
    Δ = 下一个事件的剩余时间          // 移动剩余 / 作业剩余 / 补位倒计时
    if Δ > elapsed:
      推进渲染插值到 elapsed; break   // 只写进度，不结算
    结算该事件; elapsed -= Δ
```

要点：
- **期望值驱动**：`每秒产出 = p × 单次量`，不要每 tick roll。这样时间粒度与结果解耦。
- **离线收益上限**：建议 8–12 小时，既是限损也是品类惯例。
- **第二阶段单个任务仍需 roll**：`getItemNum` 是 5–7 的区间随机数，结算瞬间 roll 一次即可（一天 120–300 次，开销可忽略）。

### 7.2 背包容量与回城频率（按新值重算）

容量 = 6 格 × 5 堆叠 = **30 个物品**（原为 10×10=100，容量降至 30%）。

| 道具 | 单次产出 | 均值 | 装满 30 个所需次数 |
|---|---|---|---|
| grain（种植） | 5–7 | 6 | **5 次** |
| mine（采矿） | 2–4 | 3 | **10 次** |

产出型任务（farming / mining）占全部 6 类任务的 **1/3**。
→ 平均每 5–10 次产出任务（即约 **15–30 个总任务**）触发一次回城。

按 **`speed = 20`、真实路网 128 个任务/天** 代入：

| 主导道具 | 装满所需该类任务 | 折合总任务数 | **回城频率** |
|---|---|---|---|
| grain（均值 6） | 5 次 | ≈ 15 个 | **≈ 8.5 次/天**（约每 2.8 小时一次） |
| mine（均值 3） | 10 次 | ≈ 30 个 | **≈ 4.3 次/天**（约每 5.6 小时一次） |

→ 实际两者并存，**回城约 5–9 次/天**，即在线 1 小时大致能看到 0–1 次。

**结论：30 容量是对的**——原 100 容量会让回城几乎不触发，30 容量下回城成为稳定可见但不过度频繁的循环环节。

> ⚠ 需确认：容量是按「总格数」计（`ceil(grain/5) + ceil(mine/5) ≤ 6`），还是按「堆叠组数」计。建议**按格数**，与 `backPackSlotNum` 字面一致。

### 7.3 任务列表的供需平衡（新分析）

补位周期 `180 s`，槽位 `7`。稳态下**空槽数 = 180 ÷ 单任务周期 T**：

以 **`speed = 20`** 代入真实路网距离（同城平均 4.4 格 / 全图平均 30.8 格）：

| 场景 | 路程 | 单任务周期 T | 稳态空槽数 | 可见性 |
|---|---|---|---|---|
| **全图随机（默认基线）** | 30.8 格 | **675 s（11.2 分）** | **0.27** | 列表几乎恒满，空槽罕见 |
| 玩家精排成同城连做 | 4.4 格 | **148 s（2.5 分）** | **1.21** | 常驻 1 个空槽，节奏可感知 |
| 同点位连做（移动≈0） | 0 格 | 60 s | **3.0** | 常驻 3 个空槽 |

**三个结论：**

1. **不会空转。** 抽干 7 个槽需要 T < 25.7 s，而 `needTime = 60` 已超过，角色永远有活干 ✅
2. **默认节奏下补位机制不可见**（空槽 0.27 个）——列表长期是满表，玩家看不到"补充中"。这是**可接受的**：列表满意味着不缺活干，符合挂机友好；代价只是 `initTaskListSlot` 的成长感偏弱。
3. **玩家精排顺序 = 空槽变多**，这形成一个有趣的反向关系：越会玩、跑得越快，越需要等任务补位。若将来觉得这是惩罚，可用"补位周期随移速技能缩短"来抵消。

> 建议：**补位周期不要固定 180 s，而应让它与单任务周期保持可感知的比例**（`补位周期 ≈ 60%–80% × 单任务周期`）。此项可后置，第一版先用 180 s 跑通。

源数据：`$map` 页签 **B2:AJ31**（36 列 × 30 行），其中值为 `1` 的格子为道路格，共 **80 个**。

坐标映射已验证：`mapNode.position` 的 `(X, Y)` ↔ `$map` 单元格 `(行 = 1+Y, 列 = 1+X)`，
16 个节点逐格核对全部命中对应汉字（府/兵/市/田/酒/书/矿），city 确认为 **2×2 = 4 格**。

处理步骤（2026-10-01 改为「点 + 自动连边」方案）：
1. 从 `$map` 提取 80 个道路格 → **逐格写入 `mapRoad`**（tag 1–80，`roadType` 预留列填 `plain`）
2. `mapNode` 只保留 **16 个设施/州府**（道路点不再混入，任务系统无需过滤）
3. 建图（80 道路格 + 16 节点，4 邻域，设施多格合并）→ **96 点 97 边、单连通分量、无孤立点** ✅
4. **边不落表**，由坐标四邻域自动推导；距离一律走 Dijkstra
5. 旧 `mapRoute` 改名为 `$mapRoute` 留档

> 已验证：新方案与旧压缩边方案在 **120 对设施两两最短路**上结果完全一致，
> 5 条基准路径（6 / 22 / 31 / 37 / 55）全部命中，平均 30.75 格。

### 8.2 路网结构

```
上庸 ──17格── 25:7 ──1格── 新野          （新野是唯一远端分支）
  │
  1格
  │
11:12 ──14格── 19:18 ──15格── 30:22 ──1格── 襄阳
                   │
                 13格
                   │
                 永安
```

4 个州府是枢纽，12 个设施是叶子，形状接近「一条主干 + 一个分支」。
（括号内为分叉点的 `mapRoad.position`，对应旧的 road18/20/21/22）

### 8.2b 路况扩展：`roadType` 预留列

`mapRoad.roadType` 当前全为 `plain`，是为「一条路一半山路一半树林」预留的扩展点。

| 方案 | 能否表达「同一条路分段不同路况」 |
|---|---|
| **旧 `mapRoute`（压缩边）** | ❌ 不能。一条边只有一个 `length`，要分段必须**拆边改拓扑** |
| **`mapRoad`（逐格）** | ✅ 能。给对应格子填不同 `roadType`，结构不变 |

启用后两处必须跟着改：

1. **Dijkstra 边权**从「恒定 1 格」改为「按目标格的成本」——即寻路优化的是**时间**而非格数
2. **UI 与任务卡显示的"路程"要换成"预计耗时"**（同样 10 格，官道 120 秒 / 山路 300 秒，
   对玩家有意义的数字是后者）

### 8.2c 性能：不要缓存 `mapRoute`

实测（Node 22，96 点 103 边，朴素 O(V²) Dijkstra，未用堆优化）：

| 指标 | 实测值 |
|---|---|
| 单次寻路 | **15.7 微秒** |
| 一天 128 个任务（128 次寻路） | **2.0 毫秒** |
| 离线 8 小时补算（约 43 次） | **0.7 毫秒** |
| 启动时预计算 16×16 全表 | 3.8 毫秒（一次性） |

**结论：寻路开销可忽略，缓存 `mapRoute` 带来的性能收益毫无意义。**
真正的实现红线是**不要每帧重新寻路**——应在接取任务时算一次路径并缓存该路径的格子序列，
之后每帧只沿序列插值移动。

> ⚠ 更关键的是：一旦 `roadType` / 坐骑 / 官道解锁会改变边权，**预计算的边长缓存就会失效**。
> 所以正确的切分是：**路径的格子序列可静态缓存，耗时必须按当前能力实时算。**

### 8.3 新野是远端分支（✅ 已确认：保持现状，不补路）

新野（右上）**只有一条出路**——经 road21 走 17 格回上庸（左上），没有任何路连到 Y=18 的主干道。
`$map` 中 X 20–30、Y 8–17 这片区域完全空白。

> **2026-10-01 决策：不补路。** 新野作为**有意设定的偏远州**保留——它给地图带来真实的距离梯度，
> 是「远州高价值 / 长途物流成本」这一设计意图的载体，也是第二层移速技能存在意义的来源。

距离矩阵（设施两两最短路，共 96 对）：

| 指标 | 真实路径 | 早期曼哈顿估算 |
|---|---|---|
| 同州府设施间距 | 平均 **4.4 格**，最大 6 | 5.0 |
| 跨州府设施间距 | 平均 **37.3 格**，最大 **55**，最小 18 | 23.5 |
| 全部设施对平均 | **30.8 格** | 19.8 |

最远 6 对全部是 **新野 ↔ 襄阳**（55 / 53 格），是直线距离（21 格）的 **2.6 倍**。
梯度本身是有价值的（近/中/远三档），但要注意：新野相关的任务天然是「低效任务」，
将来若做任务权重倾斜，应给它对应的高价值补偿，否则玩家会持续想刷掉它。
